# Evaluation methodology and study procedure

## Reproducible synthetic regression

Run `node evaluation/benchmark_accuracy.js` after `pnpm install --frozen-lockfile`.
It executes the production `score_compatibility` SQL using local PGlite, saves
`evaluation/results/synthetic-v1.json`, and records engine/dataset SHA-256 hashes.
The browser evaluation page displays this saved output; it does not run a different engine.

The dataset is exactly 10 developer-authored profiles and 12 synthetic jobs. Existing relevance lists are
not independently judged ground truth. Fixture descriptions are formed from the supplied domain keywords;
required technical skills are required, preferred technical and listed soft skills are preferred in this fixture
mapping. These are fixture decisions, not claims about verified vacancies or a representative real corpus.

Definitions, for each profile with relevant set R and a unique ranked list:

- P@K = relevant retrieved in first K / K, including when fewer than K results exist.
- Recall@K = relevant retrieved in first K / |R|.
- F1@K = harmonic mean of that profile's P@K and Recall@K, zero if both are zero.
- AP = sum of precision at each relevant rank over the entire returned ranking / |R|.
- MAP = arithmetic mean of AP across profiles. It is not truncated MAP@5.
- The summary averages each profile metric equally (macro averaging). Macro F1 is the average of per-profile
  F1 values, not the harmonic mean of aggregate precision and recall.
- Profiles with no relevant jobs receive recall/AP/F1 zero and remain in the denominator; report their count.
  Missing judgments must not be silently treated as irrelevant. Judging the entire corpus is necessary for recall/AP.

Recorded synthetic run: mean P@3 0.7333333, P@5 0.58, P@10 0.32, Recall@5 0.935,
macro F1@5 0.6949206 and MAP 0.8967857. See the JSON for exact per-profile results. These are regression results,
not evidence of independent recommendation quality. SQL time in that file is local execution time only.

## Independent relevance study (uncollected)

Use `evaluation/study/blind-relevance.csv`, generated by `node scripts/study-materials.cjs`.
It contains all 120 profile/job pairs in a deterministic order unrelated to scores, with profile attributes and
job requirements but no system score, rank or developer relevance label. Give each judge a separate copy.
Recruit 2–3 judges who did not author the scoring implementation; record their qualifications anonymously.

For each pair, enter 1 if the opportunity is reasonably relevant to the profile's skills, field, interests and
entry-level goal, otherwise 0. Give a short reason. Relevance is not certainty of hiring. Missing requirements
can justify a zero even when the title looks suitable. Judges should work independently without seeing scores
or one another's answers. Resolve disagreements only after preserving original ratings; define majority vote
for three judges or an independently documented adjudication for two. Report agreement (e.g. Cohen's kappa
for two binary judges), disagreements and the adjudication rule. Do not manufacture consensus.

The existing fixture set has already been inspected during development. Use it for piloting the instructions,
not as a claimed untouched final test set. Freeze the engine, choose new profiles/jobs for final evaluation,
version/hash them, and keep tuning profiles separate. Judge every job for each final profile. Run the frozen SQL
engine, join judgments by profile/job ID, and calculate metrics using `evaluation/metrics.js`. Report the full
sample, number of unjudged pairs, per-profile metrics and macro averages. Do not rerun tuning on final labels.

## Usability study (uncollected)

Planning target: 15 students/fresh graduates, subject to supervisor approval. Collected in this work: 0.
This explicitly replaces the earlier contradictory 30 versus 10–15 targets. FYP1's 50 questionnaire responses
and four elicitation interviews are different studies and must not be counted as FYP2 usability participants.

Use `participant-tasks.md`, `sus-questionnaire.md`, and the header-only CSV templates under `evaluation/study/`.
Obtain informed consent, assign anonymous codes, record task completion/time/assistance/errors, and administer
all ten SUS items immediately afterward. Do not omit unsuccessful participants from the report without explanation.

For odd items subtract 1 from the response; for even items subtract the response from 5. Sum and multiply by 2.5.
`evaluation/sus.cjs` implements and tests this rule. Each answer must be an integer 1–5; incomplete questionnaires
are invalid, not zero-filled. Report actual N, exclusions, individual scores, mean, standard deviation and range.
SUS is a 0–100 scale, not a percentage of tasks completed. Any threshold/grade interpretation needs a cited
external source and a predeclared criterion; none is claimed as achieved here.

## Performance

FYP1 PR-3: acknowledgement <=5 seconds; PR-4: recommendation results <=3 seconds under normal load.
`tests/live-browser.cjs` measures navigation start to a recommendation card visible, including the guard,
profile requests, RPC and render, for 20 sequential navigations using dedicated test accounts. Record browser,
network/context, corpus size, cold versus warm behavior, mean/median/p95/max and failures. It does not establish
concurrent-load performance. `scripts/latency.cjs` separately measures 20 live RPC round trips using dedicated
credentials supplied through environment variables; it excludes login and rendering. Never label either local
computation timing or syntax checking as end-to-end performance or functional testing.

Save raw timings under evidence, distinguish acknowledgement from completed save duration, and repeat under
specified concurrent load before claiming PR-6. Do not infer a pass from architecture or a single fast request.
